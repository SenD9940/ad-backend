# 스마트스토어 상품 및 판매 성과

워크스페이스에 저장한 스마트스토어 채널로 판매 중인 상품과 결제일 기준 판매 성과를 조회한다. 기존 `MANUAL / SELF`, `MANUAL / SELLER`, `SOLUTION` 연결의 자격 증명을 사용하며 추가 SQL·환경변수는 없다. 상품·주문·정산 정보를 변경하지 않는다.

## 화면

- `/workspaces/{workspaceId}/connections/naver`: 저장된 채널이 있으면 상품 및 판매 성과로, 없으면 자산 편집으로 이동한다.
- `/workspaces/{workspaceId}/connections/naver/assets`: 연결·재연결과 채널 선택·저장. 저장 후 해당 채널의 성과 화면으로 이동한다.
- `/workspaces/{workspaceId}/naver/performance`: 채널 선택, 조회 기간, 성과 요약·일별 추이·상위 상품, 현재 판매 중 상품 목록. 자산 편집은 상단 링크에서 연다.

기간은 한국 시간 기준으로 시작일·종료일을 포함해 최대 31일, 오늘까지다. 기본값은 최근 7일이며 오늘·최근 30일·이번 달과 직접 입력을 지원한다. 상품 목록은 현재 상태이며 판매 성과 기간과 독립적이다. 각각의 요청 오류와 새로고침을 분리한다.

## API

서비스 Access Token과 현재 워크스페이스 멤버 권한이 필요하다. `assetId`는 저장된 자산의 **내부 ID**다. 외부 채널 번호를 경로에 넣지 않는다. 응답은 기존 `Api.body`, snake_case JSON이며 `Cache-Control: no-store`를 설정한다.

| 메서드·경로 | 응답 |
| --- | --- |
| `GET /api/workspaces/{workspaceId}/naver/stores` | `asset_id`, `connection_id`, `channel_no`, 이름·URL·재연결 여부 목록 |
| `GET /api/workspaces/{workspaceId}/naver/stores/{assetId}/products?page=1&size=20` | 판매 중인 상품, 현재 페이지, `has_next`, 조회 시각 |
| `GET /api/workspaces/{workspaceId}/naver/stores/{assetId}/sales?since=2026-09-01&until=2026-09-07` | 기간 요약, 일별 집계, 결제금액 상위 10개 상품, 조회 시각·집계 기준 |

상품 페이지는 1부터 시작하며 크기는 1~100개다. 상품은 외부 상품 번호(문자열), 이름, `SALE` 상태, 대표 이미지, 판매가·할인가·재고를 제공한다. 네이버가 제공하지 않은 할인가·재고는 `null`이다.

네이버 상품 검색은 판매자 범위이며 채널 번호 필터를 지원하지 않는다. 서버가 현재 판매자의 `STOREFARM` 채널이 선택한 하나뿐인지 확인하고 해당 유형의 판매 상품만 반환한다. 구분할 수 없는 다중 채널이면 상품 조회를 거부한다. 네이버 페이지에 다른 유형의 상품이 섞일 수 있어 필터 후 상품 수가 페이지 크기보다 작거나 0개일 수 있다. `has_next`로 계속 조회하며, 판매자 전체 건수를 채널 상품 수로 오인하지 않도록 `total_elements`는 `null`이다. [네이버 상품 목록 조회](https://apicenter.commerce.naver.com/docs/commerce-api/current/search-product)

## 판매 지표의 의미

주문 API를 `rangeType=PAYED_DATETIME`, `quantityClaimCompatibility=true`로 조회한다. `PAYED` 상태만 필터링하지 않으므로 배송 완료·구매 확정·취소·반품 주문도 집계에 포함한다. 저장한 채널의 `merchantChannelId`와 일치하는 상품주문만 사용한다. [네이버 조건형 상품 주문 조회](https://apicenter.commerce.naver.com/docs/commerce-api/current/seller-get-product-orders-with-conditions-pay-order-seller)

| 응답 필드 | 화면·계산 |
| --- | --- |
| `payment_amount` | 최초 결제금액. 기간 내 결제된 상품주문의 `initialPaymentAmount` 합계(미제공 시 동일 의미의 `totalPaymentAmount`) |
| `remaining_payment_amount` | 현재 잔여 결제금액. 해당 상품주문의 `remainPaymentAmount` 합계. 한 건이라도 미제공이면 해당 집계는 `null` |
| `paid_order_count` | 중복을 제거한 주문 번호 수 |
| `product_order_count` | 중복을 제거한 상품주문 번호 수 |
| `quantity` | 최초 판매 수량. `initialQuantity`, 미제공 시 `quantity` 합계 |
| `average_order_amount` | 최초 결제금액 ÷ 결제 주문 수. 화면은 주문이 없으면 `—` 표시 |
| `canceled_product_order_count` | 해당 기간에 결제된 상품주문 중 현재 `CANCELED`인 건수 |
| `returned_product_order_count` | 해당 기간에 결제된 상품주문 중 현재 `RETURNED`인 건수 |

취소·반품 건수는 취소 발생일별 통계가 아니며 부분 취소·반품 개수도 아니다. 잔여 금액은 조회 시점 상태를 반영하므로 같은 결제 기간을 나중에 조회하면 달라질 수 있다. 일별 집계는 판매가 없는 날도 포함하며, 상위 상품은 최초 결제금액 순으로 최대 10개다. 화면의 통화는 KRW, 기준은 `PAYMENT_DATE`, 시간대는 `Asia/Seoul`이다.

상품주문 금액에는 배송비·정산 수수료 등을 합산하지 않는다. 스마트스토어 센터의 모든 매출 지표·입금/정산금과 동일한 통계가 아니며 광고 ROAS, 방문·유입·전환율도 제공하지 않는다. 원본 필드 의미는 [네이버 상품 주문 정보 구조체](https://apicenter.commerce.naver.com/docs/commerce-api/current/schemas/상품-주문-정보-구조체)를 따른다.

## 전체 조회와 실패 처리

각 한국 날짜를 `00:00:00.000+09:00`~`23:59:59.999+09:00` 구간으로 나누고 모든 페이지를 읽는다. 날짜 경계는 겹치지 않는다. 상품주문 ID가 같은 동일 행은 한 번만 집계하고, 중복 ID의 값이 조회 중 바뀌면 재조회 오류를 반환한다.

한 번의 성과 요청은 최대 62개 논리 페이지(페이지당 300개), 전체 요청에서 공유하는 45초의 조회 예산을 적용한다. 같은 페이지의 재시도·대기와 인증 갱신도 같은 기한을 사용하며 인증 갱신 후 시간을 다시 시작하지 않는다. 한 원격 상품·주문 요청은 최대 10초이며 남은 기한이 짧으면 그 안에서 종료한다. 한도 초과·중간 요청 실패·필수 금액 누락·알 수 없는 상태는 전체 오류로 반환하며 부분 합계나 가짜 0을 반환하지 않는다. 많은 주문은 기간을 줄여 조회한다. 성공 응답에만 `complete: true`가 포함된다.

내 스토어 앱은 API별 초당 2회 제한이 있다. 상품 검색과 주문 조회에 앱 ID·API별 공유 제어를 적용해 요청 시작 간격을 최소 600ms로 유지한다. 여러 워크스페이스·브라우저 요청이나 토큰 갱신도 같은 앱의 제한을 공유한다. 고정 크기의 잠금 묶음을 사용해 메모리를 제한하며, 앱 해시가 겹치면 보수적으로 순차 처리한다. 이 제어는 서버 프로세스 내부 기준이므로 동일 앱을 사용하는 여러 서버 인스턴스를 운영할 때는 공유 큐 또는 분산 호출 제한이 필요하다. [네이버 공식 호출 제한 안내](https://github.com/commerce-api-naver/commerce-api/discussions/6)

읽기 전용 상품 검색·주문 조회에서 429 또는 일시적인 500·502·503·504는 같은 요청을 최대 2회 더 시도한다. 기본 대기는 1초·2초이며 `Retry-After`가 있으면 그보다 먼저 호출하지 않는다. 남은 기한 내에 대기·재시도를 할 수 없으면 종료한다. 회차 할당량 소진이나 할당량 주기를 확인할 수 없는 오류는 자동 재시도하지 않는다. 인증·권한 오류, 잘못된 요청과 성공 응답의 해석 오류도 이 정책으로 재시도하지 않는다. [네이버 공식 429 재시도 안내](https://github.com/commerce-api-naver/commerce-api/discussions/2123)

저장 자산·연결·채널의 관계, 멤버 권한, 자격 증명과 솔루션 구독 상태를 조회 전후에 확인한다. 주문 페이지 사이에도 다시 확인한다. 토큰 만료 시 기존 발급 방식으로 갱신하고 판매자 UID를 검증하며, 인증 만료 오류만 한 번 재발급·재조회한다. 앱에 상품/주문 조회 권한과 서버 허용 IP 설정이 필요하다. 원격 오류 본문, 토큰·시크릿, 구매자 이름·주소·전화번호를 API 응답이나 로그에 포함하지 않는다. 구매자 개인정보는 집계 DTO나 DB에 저장하지 않는다.

## 검증

모의 HTTP로 상품·주문 공식 형식, 채널 필터, 시간대·페이지네이션, 금액 누락, 비밀정보·구매자 정보 비노출을 검증한다. 서비스·비즈니스·MVC 테스트로 저장 자산과 멤버 권한, 재연결 상태, 토큰 갱신, 전체 조회 한도, 기간·중복 집계, snake_case 계약을 검증한다. 프런트는 모의 API로 저장 후 이동·기간·채널 변경·부분 실패·재시도·반응형 화면을 확인한다.

2026-09-23 로컬에 설정된 앱으로 SELF 토큰 발급, 판매자·채널 검증 후 상품과 전일 결제 주문의 실제 읽기 전용 조회에 성공했다. 해당 시점 응답은 판매 중 상품 0개, 전일 상품주문 0개였으며 빈 기간 집계까지 확인했다. 이 검증에서는 DB·상품·주문을 변경하지 않았다. 실제 판매 데이터가 있는 응답은 모의 HTTP와 집계 테스트로 검증했다.

2026-09-28 기존 코드의 최근 7일 연속 조회에서 네 번째 요청까지 성공한 뒤 다섯 번째 주문 요청이 `429 / GW.RATE_LIMIT`으로 거절되는 현상을 재현했다. 응답 헤더의 초당 충전량은 2, 최대 버스트는 4였으며 잔여 호출량이 0으로 줄었다. 앱별 호출 간격, 같은 페이지의 제한적 재시도, 남은 기한·회차 할당량 처리를 추가했다. 테스트는 실제 대기 대신 제어 가능한 시계로 재시도 횟수·대기 간격·공유 앱 제어·기한 종료와 원본 정보 비노출을 확인한다.

수정한 코드로 같은 최근 7일 조회를 다시 실행해 7회 모두 HTTP 200을 확인했다. 잔여 호출량은 2~3으로 유지되었으며 429는 발생하지 않았다. 실제 진단은 본인 스토어의 읽기 전용 조회였고 DB·상품·주문을 변경하지 않았다.


주문별 결제·배송 조회와 발주·발송·취소/반품 승인, 일별 정산은 상품·판매 성과 화면의 **주문 관리**에서 제공합니다. 사용법과 처리 범위는 [주문 관리 문서](naver-order-management.md)를 참고하세요.
