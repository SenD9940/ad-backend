# 고객 승인 기반 기술 지원

고객 직접 신청은 **신청·약관 동의 → 토스페이먼츠 9,900원 결제 → 관리자 지원 시작** 순서입니다. [고객 신청·결제 설정](customer-support-payments.md)을 먼저 참고하세요. 이 문서의 관리자 등록·수동 수납 절차는 기존 `ADMIN` 요청의 호환 흐름입니다. `CUSTOMER` 요청은 추가 고객 승인이나 수동 수납 처리를 하지 않습니다.

관리자는 기존 회원·워크스페이스·연결 관리 기능을 그대로 사용한다. 고객 화면을 대신 조작할 때는 별도의 지원 요청과 고객 승인을 받고, 그 요청의 워크스페이스와 작업 권한으로 제한된 지원 세션을 사용한다.

관리자 화면은 `/admin`, 기술 지원 관리 화면은 `/admin/support`, 고객 승인 화면은 `/workspaces/{workspaceId}/support`다. 고객 승인 화면은 해당 워크스페이스의 **현재 소유자**만 사용할 수 있다.

## 운영 순서

1. 관리자가 지원 요청을 만든다. 대상 회원은 현재 워크스페이스 소유자여야 하며, 제목·작업 설명·조회 또는 조작 권한·지원료를 입력한다. 생성한 관리자가 담당자가 된다.
2. 고객이 일반 서비스 계정으로 로그인하여 요청의 범위와 금액을 확인하고 승인한다. 승인은 7일간 유효하다. 관리자는 고객 대신 승인할 수 없다.
3. 관리자가 실제 입금을 확인한 후 수납 상태를 기록한다. 유료 지원은 양수 금액과 수납 확인 번호가 필요하다. 금액이 0원인 요청은 무료 처리한다.
4. 담당 관리자가 지원 화면을 연다. 서버는 승인·수납·현재 소유권·회원 상태를 확인하고 최대 15분 동안 유효한 지원 세션을 발급한다. 승인 만료가 더 빠르면 그 시각에 함께 만료된다.
5. 기존 고객 화면에서 승인된 작업을 수행한다. 지원 중임을 표시하는 배너와 종료 동작을 제공하며, 요청마다 서버에서 권한과 유효성을 다시 확인한다.
6. 작업 후 세션을 종료하고 지원 요청을 완료한다. 고객은 승인 철회로 진행 중인 지원을 중단할 수 있고, 관리자도 요청 취소 또는 세션 종료를 할 수 있다.

승인과 수납 확인은 각각 별도 상태다. API는 작업 시작 전에 수납 확인을 먼저 기록하는 것도 허용하지만, **두 조건이 모두 충족되어야** 지원 세션을 시작할 수 있다.

## 수납 방식과 상태

현재 구현은 **수동 입금 확인 기록**이다. Toss Payments 결제창·결제 승인·웹훅·취소·환불과 연결되어 있지 않으며, `PAID`를 저장해도 결제 대행사에 청구하거나 입금을 조회하지 않는다. Toss Payments 연동은 추후 별도로 구현한다.

금액은 원화 정수 `amount_krw`이며 범위는 0~1,000,000,000원이다. 요청 생성 후 대상 회원·워크스페이스·담당자·작업 범위·금액은 수정하지 않는다. 내용을 변경하려면 기존 요청을 취소하고 새 요청을 만들어 고객 승인을 다시 받는다.

| 요청 상태 | 의미 |
| --- | --- |
| `REQUESTED` | 고객 승인 대기 |
| `APPROVED` | 고객 승인 완료. 수납 확인과 승인 유효기간을 충족하면 시작 가능 |
| `IN_PROGRESS` | 지원 세션을 시작한 요청. 세션만 종료하면 이 상태를 유지 |
| `COMPLETED` | 지원 완료. 세션 종료 및 재시작 차단 |
| `CANCELLED` | 관리자 취소 또는 고객 철회. 세션 종료 및 재시작 차단 |

| 수납 상태 | 조건 |
| --- | --- |
| `UNPAID` | 수납 미확인 |
| `PAID` | 지원료가 양수이고 `payment_reference`가 있는 수동 수납 기록 |
| `WAIVED` | 지원료가 0원인 무료 지원 |

수납 상태 변경은 `REQUESTED` 또는 `APPROVED`에서만 가능하다. `IN_PROGRESS` 이후 금액·수납 변경이나 환불 기능은 제공하지 않는다. `COMPLETED` 또는 `CANCELLED` 요청은 다시 열지 않는다.

## 인증과 접근 범위

일반 서비스 JWT, 관리자 JWT, 지원 토큰은 서로 다른 인증 수단이다. 지원 세션 발급 시에는 관리자 JWT를 사용하고, 고객 화면에서는 발급된 지원 토큰만 `X-Support-Token` 헤더로 보낸다.

```http
GET /api/workspaces/10/meta/insights?since=2026-09-01&until=2026-09-28
X-Support-Token: <지원 세션 발급 응답의 access_token>
```

지원 토큰은 32바이트 난수에서 만든 43자 문자열이며 JWT가 아니다. DB에는 SHA-256 해시만 저장하고, 원문은 발급 응답에서 한 번 전달한다. 목록·상세·감사 기록에서는 토큰과 인증 버전을 반환하지 않는다. 토큰을 URL이나 쿼리에 넣지 않는다.

프론트엔드는 관리자 세션과 지원 세션을 서로 다른 `sessionStorage` 항목으로 보관한다. 일반 고객 로그인 정보를 지원 토큰으로 덮어쓰지 않는다. 지원 요청이 거절되면 일반 고객 토큰으로 재시도하지 않는다.

서버는 매 요청에서 다음을 확인한다.

- 세션이 종료되지 않았고 유효기간이 남아 있는지
- 요청이 `APPROVED` 또는 `IN_PROGRESS`이고 고객 승인과 수납 확인이 유효한지
- 세션과 요청의 담당자·고객·워크스페이스·작업 권한이 정확히 일치하는지
- 담당자가 현재 정상 이용 중인 관리자이고, 고객도 정상 이용 상태인지
- 두 계정의 현재 인증 버전이 발급 당시와 같은지
- 고객이 여전히 해당 워크스페이스의 소유자인지

회원 정지·관리자 권한 변경·계정 세션 강제 종료·소유권 이전도 후속 지원 요청을 차단한다. 다른 관리자가 수납을 기록하거나 지원을 종료할 수는 있지만, **고객 화면에 접근하는 세션은 지정된 담당 관리자만 발급**할 수 있다.

지원 토큰으로 허용하는 경로는 코드의 명시적 목록으로 관리한다. 새 서비스 API를 추가해도 지원 권한에 자동 포함하지 않는다. URL은 매핑된 경로와 숫자 ID가 일치해야 하며 다른 워크스페이스는 접근할 수 없다.

| 권한 | 허용 기능 |
| --- | --- |
| `READ_ONLY` | 해당 워크스페이스 상세, 저장된 연결과 선택 가능한 Meta 자산·네이버 채널, Meta 캠페인·성과·페이지, 스마트스토어 상품·판매 성과·상품 등록 옵션 조회 |
| `OPERATE` | 위 조회 + Meta 광고·캠페인 생성, 광고·광고세트·캠페인 이름/상태/예산 수정, 광고 이미지 업로드, 페이지 저장, Meta 자산 및 네이버 채널 선택, 스마트스토어 상품 등록 |
| 공통 | 현재 지원 세션 조회·종료 |

회원 프로필, 전체 워크스페이스 목록, 멤버·소유권 변경, 고객 승인·철회, OAuth 시작·콜백, 네이버 자격증명 입력·자가 테스트 등은 지원 토큰으로 사용할 수 없다. 공개 API에도 지원 토큰이 붙으면 동일하게 제한하며, 다른 인증으로 넘어가지 않는다. 광고·상품의 실제 조작은 기존 서비스의 권한 검증과 외부 API를 통해 수행한다.

## 관리자 API

기본 경로는 `/admin-api/support`다. 일반 관리자 API와 같이 `Authorization: Bearer <관리자 JWT>`를 사용한다. `reason`은 선택 메모(최대 500자)다. 생략·null·공백이면 서버가 지원 등록·수납 기록·접속 시작/종료·완료·취소 동작을 기본 문구로 기록한다. 메모를 입력하면 앞뒤 공백을 제거해 보존한다. 사유 외 입력이 없는 작업은 `{}`로 요청할 수 있다.

| 메서드·경로 | 용도 |
| --- | --- |
| `GET /tickets` | 요청 목록. `status`, `customerUserId`, `workspaceId`, `page`, `size` 필터 |
| `POST /tickets` | 지원 범위·고객·금액을 고정한 요청 생성 |
| `GET /tickets/{id}` | 요청 상세 |
| `POST /tickets/{id}/payment` | 수동 수납 상태 기록 |
| `POST /tickets/{id}/sessions` | 담당자의 지원 토큰 발급. 이전 세션은 종료 |
| `GET /tickets/{id}/sessions` | 세션 이력. 원문 토큰·해시 제외 |
| `GET /tickets/{id}/actions` | 지원 작업 요청 이력 |
| `POST /tickets/{id}/complete` | 완료 처리 및 모든 세션 종료 |
| `POST /tickets/{id}/cancel` | 취소 처리 및 모든 세션 종료 |
| `POST /sessions/{id}/end` | 특정 세션 종료 |

요청 생성 예시:

```json
{
  "workspace_id": 10,
  "customer_user_id": 20,
  "title": "스마트스토어 상품 등록 지원",
  "description": "고객이 제공한 상품 정보와 이미지로 선택한 스토어에 상품을 등록합니다.",
  "access_mode": "OPERATE",
  "amount_krw": 50000,
  "reason": "고객의 기술 지원 신청"
}
```

수납 확인 예시:

```json
{
  "payment_status": "PAID",
  "payment_reference": "입금확인-20260928-001",
  "reason": "입금 내역 확인 완료"
}
```

세션 시작·완료·취소·종료는 다음 형태를 사용한다.

```json
{ "reason": "승인된 상품 등록 작업 시작" }
```

세션 발급 성공 시 `Api.body`:

```json
{
  "session_id": 30,
  "ticket_id": 40,
  "workspace_id": 10,
  "customer_user_id": 20,
  "access_mode": "OPERATE",
  "access_token": "<한 번만 반환되는 지원 토큰>",
  "expires_at": "2026-09-28T15:15:00"
}
```

## 고객 API

고객 승인·철회 요청에는 **일반 서비스 JWT**가 필요하다. 지원 토큰은 이 경로에서 거절한다.

| 메서드·경로 | 용도 |
| --- | --- |
| `GET /api/workspaces/{workspaceId}/support/tickets` | 현재 소유자가 자신을 대상으로 한 지원 요청 조회 |
| `POST /api/workspaces/{workspaceId}/support/tickets/{ticketId}/approve` | 작업 범위·금액 승인. `{}` 또는 선택 메모 `{ "reason": "작업 범위와 금액에 동의합니다" }` |
| `POST /api/workspaces/{workspaceId}/support/tickets/{ticketId}/revoke` | 요청 철회 및 모든 지원 세션 종료. `{}` 또는 선택 메모 `{ "reason": "지원 작업 중단 요청" }` |
| `GET /api/support/session` | 지원 토큰으로 현재 세션의 식별자·범위·만료 조회 |
| `POST /api/support/session/end` | 지원 토큰으로 자신의 지원 세션 종료 |

고객용 요청 응답은 관리자 요청과 같은 `id`, `workspace_id`, `customer_user_id`, `assigned_admin_id`, `title`, `description`, `access_mode`, `amount_krw`, `payment_status`, `status`, `approved_at`, `approval_expires_at`, `created_at`, `updated_at`을 사용한다. 내부 수납 확인 번호·기록자는 고객 응답에서 제외한다.

목록은 `Api.body`에 `items`, `page`, `size`, `total_elements`, `total_pages`를 반환한다. `page`는 0부터 시작하며 `size`는 기본 20, 최대 100이다. JSON 필드는 snake_case이고 목록 검색 쿼리 이름은 위 표처럼 camelCase다. 지원 관련 날짜는 한국 시간 기준이며 관리자 JWT의 만료 시각 형식과 구분한다.

## 감사 기록과 동시성

요청 생성, 수납 기록, 고객 승인·철회, 세션 발급·종료, 완료·취소는 `admin_audit_logs`에 기록한다. 고객 승인·철회의 행위자는 실제 고객 ID다. 이 기록이 실패하면 상태 변경도 같은 트랜잭션에서 되돌린다.

지원 토큰으로 허용된 요청은 **기존 컨트롤러를 실행하기 전에** `support_actions`에 별도 트랜잭션으로 저장한다. 기록할 수 없으면 요청을 실행하지 않는다. 행위자·고객·워크스페이스·세션·HTTP 메서드·안전한 경로·시작 시각을 남기고, 처리가 끝나면 HTTP 상태와 완료 시각을 기록한다. 유효한 세션의 범위 위반도 403 이력으로 기록한다.

요청 본문, 응답 본문, 쿼리 문자열, 토큰, 고객 입력 자료는 작업 감사 테이블에 저장하지 않는다. 기록된 경로에는 허용된 숫자 객체 ID가 포함될 수 있다. 거절한 알 수 없는 경로는 실제 입력 대신 매핑된 경로 형태만 기록한다.

변경 작업은 회원 ID 순서로 사용자 행을 잠근 다음 워크스페이스·지원 요청·세션 순으로 잠근다. 세션 발급과 고객 철회가 경합할 때는 잠금 후 요청 상태를 확인한다. 새 세션을 시작하면 기존 세션 종료와 새 발급, 감사 기록이 함께 커밋된다.

## 적용과 현재 제한

두 서버는 같은 서비스 DB의 지원 테이블을 사용한다. **서버를 배포하기 전에** 아래 마이그레이션을 순서대로 적용해야 한다.

1. 아직 적용하지 않았다면 [관리자 기본 마이그레이션](../db/migrations/20260928_admin_operations.sql): `users.auth_version`, `admin_audit_logs`.
2. [기술 지원 마이그레이션](../db/migrations/20260928_support_sessions.sql): `support_tickets`, `support_sessions`, `support_actions`.
3. 변경된 `api`와 `admin-api`, 프론트엔드를 함께 배포한다. 최초 관리자 지정은 [관리자 API 문서](admin-api.md)를 따른다.

개발 과정에서는 이 SQL을 실제 DB에 실행하지 않았다. 서비스와 관리자 서버가 이전 DB 스키마로 실행되지 않도록 배포 순서를 맞춘다. 결제 키나 Toss Payments 환경변수는 이번 기능에 필요하지 않다.

- 고객 철회나 관리자 종료는 다음 요청부터 접근을 차단한다. **이미 시작한 외부 API 요청이나 이미 생성·변경한 광고·상품을 되돌리지 않는다.**
- HTTP 오류나 타임아웃만으로 외부 변경이 실패했다고 확정할 수 없다. 광고·상품 상태를 조회해 확인한 뒤 후속 작업을 결정한다. 변경 요청을 자동 재시도하지 않는다.
- 완료 시각과 HTTP 상태가 없는 작업 기록은 처리 결과를 확정하지 못한 상태다. 기록 저장 실패 후에도 이미 수행된 작업이 있을 수 있으므로 실패로 단정하지 않는다.
- 세션 목록의 `active`는 세션 자체의 미종료·미만료를 나타낸다. 실제 요청 가능 여부는 현재 계정 상태·인증 버전·소유권·고객 승인도 함께 검증한 결과로 결정한다.
- 토큰이 만료되면 유효한 고객 승인과 수납 상태를 다시 확인하여 새 세션을 시작한다. 고객 승인이 만료되면 새 지원 요청과 승인이 필요하다.
- 이 기능은 지원료의 실제 결제, 환불, 세금계산서 발급이나 외부 광고·상품 전체 이력 동기화를 구현하지 않는다.

검증은 모의 MVC와 H2 기반 테스트로 수행하며 실제 고객 화면의 광고·상품이나 외부 결제는 변경하지 않는다.
